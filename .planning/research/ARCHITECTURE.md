### Component Responsibilities

| Component | Responsibility | Implementation |
|-----------|----------------|----------------|
| `tetragonreceiver` (factory.go) | Register receiver type, provide defaults, instantiate receivers | `receiver.NewFactory()` with `WithLogs()` |
| `tetragonreceiver` (config.go) | Hold endpoint, TLS, backoff config; validate on start | Go struct with `mapstructure` tags + `Validate()` |
| `tetragonreceiver` (receiver.go) | Manage gRPC connection lifecycle, stream loop, convert events to `plog.Logs` | Implements `component.Component` (`Start`/`Shutdown`) |
| gRPC stream loop (internal goroutine) | Open `FineGuidanceSensors.GetEvents` stream, read events, push to `consumer.Logs` | `context.WithCancel` goroutine, `Recv()` loop |
| Reconnect logic | Exponential backoff on stream error, respect `Shutdown` cancellation | `time.Sleep` with jitter, cancel check |
| Event converter | Transform `GetEventsResponse` to `plog.LogRecord` with `protojson.Marshal` body | Pure function, no state |
| `components.go` (OCB-generated) | Wire all factories into the collector binary | Generated by OCB, includes `tetragonreceiver.NewFactory()` |
| OCB manifest (`builder-config.yaml`) | Declare distribution components, versions, output path | YAML, references local module via `path:` field |
| `Containerfile` | Multi-stage build: OCB build → minimal runtime image | `golang:` build stage, `debian-slim` runtime |

### Structure Rationale

- **receiver/tetragonreceiver/:** Isolated as its own Go module so it can be tested independently and referenced by OCB's `path:` field. This is the standard contrib pattern.
- **distribution/:** Contains only the OCB manifest. OCB generates code into a temp or gitignored output directory; the manifest is the artifact to version-control.
- **config/:** Runtime YAML separate from build config. Mounted into the container at runtime.
- **converter.go:** Splitting event conversion into a pure function (no gRPC dependency) enables easy unit testing without a mock gRPC server.

## Architectural Patterns

### Pattern 1: Factory + Component Lifecycle

**What:** The OTel Collector SDK requires a `receiver.Factory` that creates receiver instances on demand. The factory is the only public entry point; the receiver struct is unexported.

**When to use:** Always — this is the mandatory SDK pattern for all receivers.

**Trade-offs:** Boilerplate-heavy but ensures the collector can manage component lifecycle uniformly.

**Key interfaces:**
```go
// factory.go
func NewFactory() receiver.Factory {
    return receiver.NewFactory(
        component.MustNewType("tetragon"),
        createDefaultConfig,
        receiver.WithLogs(createLogsReceiver, component.StabilityLevelAlpha),
    )
}

func createLogsReceiver(
    _ context.Context,
    set receiver.Settings,
    cfg component.Config,
    nextConsumer consumer.Logs,
) (receiver.Logs, error) {
    rCfg := cfg.(*Config)
    return &tetragonReceiver{
        config:       rCfg,
        nextConsumer: nextConsumer,
        logger:       set.Logger,
    }, nil
}
```

### Pattern 2: Background Goroutine with Context Cancellation

**What:** `Start()` launches a goroutine that runs the stream loop. `Shutdown()` calls the cancel function to stop it. The goroutine uses `context.Background()` (not the passed-in context) so it outlives the startup call.

**When to use:** Any receiver that drives data ingestion from a long-running external stream.

**Trade-offs:** Simple and idiomatic Go. Requires careful handling of the cancel function to avoid goroutine leaks.

```go
// receiver.go
func (r *tetragonReceiver) Start(_ context.Context, host component.Host) error {
    ctx, cancel := context.WithCancel(context.Background())
    r.cancel = cancel
    go r.streamLoop(ctx)
    return nil
}

func (r *tetragonReceiver) Shutdown(_ context.Context) error {
    if r.cancel != nil {
        r.cancel()
    }
    return nil
}
```

### Pattern 3: Reconnect Loop with Exponential Backoff

**What:** The stream loop maintains a persistent gRPC connection to Tetragon. When `Recv()` returns an error, the loop sleeps with exponential backoff + jitter before reconnecting. The loop exits when the context is cancelled.

**When to use:** Any receiver connecting to a server-side streaming gRPC endpoint.

**Trade-offs:** Must distinguish between `context.Canceled` (clean shutdown) and transient errors (retry). Must cap backoff to avoid indefinite delays.

```go
// receiver.go (pattern sketch)
func (r *tetragonReceiver) streamLoop(ctx context.Context) {
    backoff := initialBackoff
    for {
        if err := r.runStream(ctx); err != nil {
            if ctx.Err() != nil {
                return // clean shutdown
            }
            r.logger.Warn("stream error, reconnecting", zap.Error(err),
                zap.Duration("backoff", backoff))
            select {
            case <-time.After(backoff + jitter()):
            case <-ctx.Done():
                return
            }
            backoff = min(backoff*2, maxBackoff)
        } else {
            backoff = initialBackoff // reset on clean stream end
        }
    }
}
```

### Pattern 4: Pure Event Converter

**What:** Conversion from `*tetragonpb.GetEventsResponse` to `plog.Logs` is a stateless pure function in `converter.go`. It uses `protojson.Marshal` to serialize the full event as the log body, then extracts key attributes separately.

**When to use:** Any receiver that maps a source format to OTLP. Isolating conversion enables unit testing without a running gRPC server.

**Trade-offs:** Slightly more files, but conversion logic is testable in isolation and the receiver struct stays focused on connection management.

```go
// converter.go
func responseToLogs(resp *tetragonpb.GetEventsResponse) (plog.Logs, error) {
    logs := plog.NewLogs()
    rl := logs.ResourceLogs().AppendEmpty()
    sl := rl.ScopeLogs().AppendEmpty()
    lr := sl.LogRecords().AppendEmpty()

    // Full JSON body via protojson for format compatibility
    body, err := protojson.Marshal(resp)
    if err != nil {
        return logs, err
    }
    lr.Body().SetStr(string(body))

    // Extracted attributes for efficient filtering
    lr.Attributes().PutStr("event.type", resp.EventType().String())
    if resp.NodeName != "" {
        lr.Attributes().PutStr("k8s.node.name", resp.NodeName)
    }
    // ... additional attribute extraction
    return logs, nil
}
```

## Data Flow

### Event Ingestion Flow

```
Tetragon Agent (gRPC :54321)
    │
    │  server-streaming RPC: FineGuidanceSensors.GetEvents
    ▼
tetragonReceiver.streamLoop (goroutine)
    │
    │  resp, err := stream.Recv()
    ▼
converter.responseToLogs(resp)
    │  protojson.Marshal → body string
    │  EventType, NodeName, ClusterName → attributes
    │  (k8s pod info when present)
    ▼
consumer.Logs.ConsumeLogs(ctx, plog.Logs)
    │
    ▼
batch processor (buffer, timeout)
    │
    ▼
resourcedetection processor (add host/k8s attributes)
    │
    ▼
otlphttp exporter → OpenObserve :5080
```

### Component Startup Order (Collector-managed)

```
1. Extensions start (health_check, file_storage)
2. Exporters start  (otlphttp)
3. Processors start (batch, resourcedetection)
4. Receivers start  (tetragonreceiver, journald)
   └── tetragonreceiver.Start() → launches streamLoop goroutine
       └── streamLoop dials Tetragon gRPC, opens GetEvents stream
```

Shutdown is the reverse: receivers shut down first, then processors, then exporters.

```
builder-config.yaml
    │  dist: { name, output_path }

```

## Build Order (Phase Implications)

The component dependencies create a natural build order:

1. **`config.go` first** — Config struct is a dependency of factory and receiver. No external dependencies, validates assumptions about the Tetragon API surface.

2. **`converter.go` second** — Pure function, depends only on `tetragonpb` and `pdata/plog`. Can be unit tested immediately without a running collector.

3. **`factory.go` + `receiver.go` together** — Factory wires config and receiver; receiver implements lifecycle. These reference each other and `consumer.Logs`.

4. **OCB manifest** — After the receiver module compiles, add it to `builder-config.yaml` with `path:` referencing the local module.

5. **`config.yaml`** — Runtime pipeline configuration, exercised once the binary builds.

6. **`Containerfile`** — Wraps the OCB build; debuggable only after steps 1-5 succeed.

7. **CI pipeline** — Last, after all build artifacts are stable.

## Anti-Patterns

### Anti-Pattern 1: Blocking in Start()

**What people do:** Open the gRPC connection and block reading the stream inside `Start()` directly.

**Why it's wrong:** `Start()` must return quickly. Blocking prevents the collector from completing startup; other components (processors, exporters) never start, so `ConsumeLogs()` calls will fail.

**Do this instead:** Launch a goroutine in `Start()` and return immediately. Use `context.WithCancel` to stop the goroutine from `Shutdown()`.

### Anti-Pattern 2: Using the Start() Context for the Stream Loop

**What people do:** Pass the `ctx` argument from `Start(ctx, host)` into the background goroutine.

**Why it's wrong:** The collector cancels this context after `Start()` returns. The goroutine's context is cancelled immediately, terminating the stream.

**Do this instead:** Create a new context with `context.WithCancel(context.Background())` inside `Start()`, store the cancel func on the receiver struct.

### Anti-Pattern 3: One Log Record per `ConsumeLogs` Call

**What people do:** Call `ConsumeLogs` once per Tetragon event as they arrive from `Recv()`.

**Why it's wrong:** Creates excessive pressure on downstream processors. The batch processor can only batch what it receives; single-record calls defeat it.

**Do this instead:** This is actually acceptable for a streaming receiver — the batch processor downstream handles batching. Do NOT buffer inside the receiver; that duplicates batch processor logic and adds memory complexity. One `Logs` object per `Recv()` event is correct for a streaming receiver.

### Anti-Pattern 4: Embedding the Receiver Module Directly (No Separate go.mod)

**What people do:** Put the receiver source in the root module alongside the OCB manifest.

**Why it's wrong:** OCB generates its own `go.mod` in the output directory. A separate receiver module with its own `go.mod` is required for the `path:` field reference to work correctly, and for independent testing.

**Do this instead:** Create `receiver/tetragonreceiver/go.mod` as a standalone module. Reference it in the OCB manifest with both `gomod:` (module path) and `path:` (local filesystem path).

### Anti-Pattern 5: Copying Tetragon protobuf files instead of importing the module

**What people do:** Copy `tetragon.pb.go` files into the receiver to avoid a dependency on `github.com/cilium/tetragon/api`.

**Why it's wrong:** The Tetragon API evolves; copied protos will drift. `protojson.Marshal` produces different output if the proto descriptor doesn't match exactly.

**Do this instead:** Import `github.com/cilium/tetragon/api/v1/tetragon` as a Go module dependency. Pin the version in `go.mod`.

## Scaling Considerations

This is a single-node agent deployment, not a scalable service. Scaling considerations are about throughput and resilience, not horizontal scaling.

| Concern | Current Target | If Event Rate Spikes |
|---------|---------------|----------------------|
| Event throughput | ~100-1000 events/sec typical | Batch processor absorbs bursts; back-pressure propagates to Tetragon via gRPC flow control |
| Memory | Low — streaming, not buffering | Increase batch processor `send_batch_max_size` to shed load |
| Connection stability | Single gRPC stream with backoff | Already handled by reconnect loop; Tetragon rate_limit events signal overload |
| Multiple nodes | One collector per node (DaemonSet) | Each collector connects to local Tetragon only; no cross-node coordination needed |
